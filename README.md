# lineage

> **Preliminary documentation.** lineage is a work in progress; features and the data format may still change.
>
> **Heavily AI-assisted.** lineage is my first try at AI-assisted coding; most of the code, tests and documentation in this repository were written by an AI coding assistant (Claude, by Anthropic), directed and reviewed by a human. Treat it accordingly: read the code before relying on it, and keep backups of your data.

lineage is a small, self-hosted, single-user tool that **generalises the git workflow**: branches, commits, forks and merges, plus states and typed references between lines of work. Each project is a branch, drawn as a lane on a timeline; its milestones are its commits. A project can fork from another project's milestone, merge into another project, or refer to work it builds on.

Initially I intended lineage to become a manager for my papers and theses; quite soon enough I realized it could be a method for graphically illustrating projects and workflows based on milestones, relationships and dependencies. For instance, the git workflow can be imported into a paper's development cycle: "commits" are versions of the paper that are generated by authors at specific dates or meetings, "preprints" are self-published and/or not-per-reviewed versions, "submitted" is self-explanatory. Talking to friends in other areas I noticed that their workflow was also quite like this one; therefore, I built lineage so that nothing in the model is tied to a particular domain. The starter vocabulary and the example data happen to describe academic papers and code development as the first use cases, but kinds, states, reference types and markers are all yours to define.

All data lives in plain files (one YAML file plus Markdown descriptions) that you can read, edit by hand, back up and version. The idea is portability and simplicity.

## Concepts

| Term | Meaning | git equivalent |
|---|---|---|
| Workspace | everything below | repository |
| Group | a set of projects drawn together (e.g. a research thread) | closest: a branch namespace such as `feature/*` |
| Project | a line of work (e.g. a paper) | branch |
| Milestone | a dated step in a project | commit |
| Fork | a project started from a milestone of another project | a branch created from a commit (`git branch new <commit>`) |
| Merge | a milestone that brings in milestones of other projects | merge commit (a commit with several parents) |
| Head | a project's latest milestone that has happened | branch tip |
| Planned milestone | a milestone dated in the future, not yet reached | none: git has no future commits |
| State | the condition a project is in from one milestone until the next (drafting, under review…) | none: git does not record what happens between commits |
| Reference | a typed link between milestones of different projects (builds on, companion…) | closest: a commit message that cites another commit, but typed and drawn |
| Kind | the type of a milestone (draft, submitted, published…), shown as its symbol | closest: a commit type, as in Conventional Commits (`feat:`, `fix:`) |
| Marker | a flag you attach to milestones (warning, open question…) | closest: a tag on a commit |

What is derived (never stored):

- Within a project, milestones are ordered by date, then by creation order; each one's parent is the previous one.
- A **fork** is a project whose `from` points at another project's milestone; a **merge** is a milestone whose `merges` lists milestones of other projects.
- A project's **head** is its latest non-planned milestone; its **current state** is the head's state; **time in state** is today minus the head's date. A project whose head is merged elsewhere is **merged**.

Kinds, states, reference types and markers are your own vocabulary, edited in Settings. Every entity can have a **description** in Markdown with LaTeX math (`$…$` inline, `$$…$$` display).

## What you can do

- **Timeline:** lanes per project, grouped, with forks drawn under their origin. You can pan and zoom, and switch between a time axis and event order. Drag a lane label to reorder projects or move them (with their forks) to another group.
- **Lines and symbols:**
  - each kind has a symbol shape and size
  - each state and reference type has a line pattern, colour, opacity and thickness
  - any single lane line or reference can carry its own text (position, alignment, size; references can run the text along the line)
  - markers (warning, question, chain, flag…) can be attached to milestones
- **Side panel:** click anything to see it and edit it. Fork from a milestone, merge into another project, or add a reference by clicking its target on the timeline.
- **Deleting:** you get a confirmation listing everything that will be removed, or what is blocking the delete.
- **Undo:** every change can be undone, from the toast after the change or the Undo button.
- **Status board:** projects in three columns ("On me", "On others", "Inactive"), sorted by time in state.
- **Dependencies view:** projects as a graph, earlier work at the bottom.
- **Hover** anything to highlight its ancestors and descendants. **Filters** by group, state and activity are shared by all three views.
- **Hand edits:** changes to the files on disk show up in the page within about 5 seconds.

## Running it with Docker

Requirements: Docker with Compose. Nothing else is needed on the machine, and the running app needs no internet access.

```sh
mkdir data                        # or: cp -r examples/papers data   (to start from the example)
docker compose up -d              # builds the image the first time
```

Open http://localhost:8080. Your data lives in `./data` next to `docker-compose.yml`; an empty `data/` folder gets a starter vocabulary on first start.

- **Create `data/` yourself before the first start.** If Docker creates it, it belongs to root and lineage cannot write to it.
- **Your user:** the container runs as user and group id 1000 so that files in `data/` stay yours. If `id -u` / `id -g` print something else, start it with `LINEAGE_UID=$(id -u) LINEAGE_GID=$(id -g) docker compose up -d`. To make that permanent, put the two values in a `.env` file next to `docker-compose.yml` (`printf 'LINEAGE_UID=%s\nLINEAGE_GID=%s\n' $(id -u) $(id -g) > .env`); Compose reads it automatically.
- **Only reachable from this machine:** the port is published on `127.0.0.1` because the data may describe unpublished work and there is no authentication. The comments in `docker-compose.yml` explain how to expose it on your network or behind a reverse proxy.
- **Updating** after pulling new code: `docker compose up -d --build`. **Logs:** `docker compose logs -f`. **Stop:** `docker compose down` (your data stays in `data/`).

## Running it from source (development)

Requirements: Python 3.12 or newer, Node.js 22.12 or newer.

```sh
# 1. Backend dependencies (once)
python -m venv .venv
.venv/bin/pip install -e "./backend[test]"

# 2. Frontend dependencies (once)
cd frontend && npm install && cd ..

# 3. Start the backend with the example data (see below), on http://localhost:8000
cp -r examples/papers data        # only if data/ does not exist yet
DATA_DIR=./data .venv/bin/uvicorn --factory backend.app:create_app

# 4. In another terminal, start the frontend dev server on http://localhost:5173
cd frontend && npm run dev
```

The dev server forwards `/api` to `http://localhost:8000` (override with `API_URL=http://host:port npm run dev`).

To run everything from the backend alone, build the frontend once with `cd frontend && npm run build`. The backend then also serves the app at http://localhost:8000.

If `DATA_DIR` points at a folder that does not exist yet, lineage creates it with a starter vocabulary (kinds, states and reference types for papers) and no projects.

## Example data

`examples/papers/` is a complete data folder with fictional papers. It exercises every feature: forks (including across groups), a merge, both reference types, every kind and state, markers, planned and overdue milestones, and descriptions with math. Copy it to use it:

```sh
cp -r examples/papers data
```

Do this only when `data/` does not exist yet (otherwise `cp` puts the files in `data/papers`). Copy rather than point `DATA_DIR` at `examples/papers` directly: lineage writes to its data folder.

## Your data

```
data/
  workspace.yaml                # all entities except descriptions
  descriptions/<type>/<id>.md   # one Markdown file per entity that has a description
  .history/<timestamp>/         # snapshots taken before each change (the last 20), used by Undo
```

`<type>` is one of `groups`, `projects`, `milestones`, `references`, `kinds`, `states`, `reftypes`, `markers`.

- **Writing:** every change is checked against the whole workspace before anything is written; invalid changes are rejected with a message and leave the files untouched. Files are written atomically.
- **Undo:** restores the most recent snapshot, one step at a time. There is no redo.
- **Hand edits** to `workspace.yaml` or the description files are picked up automatically. If a hand edit leaves the workspace invalid, the page shows the problems until you fix the file. Comments in `workspace.yaml` are not kept when lineage writes it.
- **Ids** are made from the name or title when an entity is created and never change, so renaming is safe.
- **Backups:** copy the whole data folder, or keep it in git. It is plain text and diffs well. `data/` is in this repository's `.gitignore` because it may describe unpublished work.

## Security

There is no authentication. By default it is meant to be reached from your own machine only (the Docker setup publishes it on `127.0.0.1:8080`). If you expose it on a network, put it behind a reverse proxy that does authentication.

## Tests

```sh
cd backend && ../.venv/bin/pytest        # backend: validation, derived data, delete rules, storage, API
cd frontend && npm test                  # frontend: layout, colours, lanes, scales, filters, views
```

## Regenerating the API types

The frontend's TypeScript types are generated from the backend's OpenAPI schema; never edit `frontend/src/api/schema.d.ts` by hand. With the backend running on port 8000:

```sh
cd frontend && npm run gen-api
```

The interactive API documentation is at http://localhost:8000/docs while the backend runs (that page loads its scripts from a CDN, so it needs internet; the app itself does not).

## Project layout

- `backend/`: FastAPI app: `models.py` (data model), `graph.py` (derived data, validation, delete rules), `store.py` (files, snapshots, undo, reload), `app.py` (routes), `seed.py` (starter vocabulary), `tests/`.
- `frontend/`: Svelte 5 + Vite + TypeScript single-page app: `src/layout` (pure, tested layout functions), `src/views`, `src/components`, `src/api` (generated types + fetch wrapper).
- `examples/`: example data.
- `Dockerfile`, `docker-compose.yml`: the image (frontend built with Node, served by a single uvicorn worker) and how to run it.
